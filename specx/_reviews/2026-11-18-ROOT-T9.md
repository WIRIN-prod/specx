## Findings

**F1**
- **ID:** F1
- **Severity:** high
- **Where:** `plugins/specx/skills/plan/SKILL.md:26` ("Write `—` in the new cell of every existing row."). Spec `specx/spec.md:788` (ROOT-T9 Steps, item 2: "Add each missing column with `—` in every row.").
- **Problem:** The text says "the new cell" (singular). A 7-column project lacks two columns (`Type`, `Milestone`). The text does not say to write one dash for each missing column. The literal reading writes one dash per row. The approved step says each missing column gets a dash.
- **Failure scenario:** Simulated on the 7-column fixture with the literal reading: the header has 9 cells, and each data row has 8 cells. The `—` for `Type` lands under `Type`, and the `Milestone` cell is missing. Every row from then on is one cell short. The next run sees no missing header column, so it never repairs the rows.
- **Remedy:** Replace the bullet with: "For each listed column, write `—` at the end of every existing row, so every row has one new cell per listed column." Keep the spec wording in step with this text.

**F2**
- **ID:** F2
- **Severity:** high
- **Where:** `plugins/specx/skills/plan/SKILL.md:27` ("Keep every existing column, cell, and row."). Also `:25` and `:26`.
- **Problem:** The text does not say how to edit a row. It does not say how to treat `\|`, an escaped pipe inside a cell. A reader that splits each row on `|` and joins it again changes the cell text.
- **Failure scenario:** Simulated on the row `| ROOT-T2 | Pipe \| in cell | ... |`. The split-and-join method produced `Pipe \ | in cell`. The cell text changed and the Markdown table breaks. The user loses the exact cell text. No rule in the step stops this.
- **Remedy:** Add a sentence: "Append the new cells to the end of each row text. Do not split and join the row, so escaped pipes `\|` and empty cells stay as they are."

**F3**
- **ID:** F3
- **Severity:** medium
- **Where:** `plugins/specx/skills/plan/SKILL.md:26`.
- **Problem:** A row shorter than the old header has fewer cells than the header. The text does not say to pad it first. Two readings give different results. The literal reading gives the short row 6 cells against a 9-cell header. The padded reading gives 9 cells.
- **Failure scenario:** For fixture row `ROOT-T4` (5 cells before, header 7 cells), the literal reading leaves the row 2 cells short. The padded reading gives a valid row.
- **Remedy:** Add: "If a row has fewer cells than the old header, add empty cells until it matches the old header, then add the new cells."

**F4**
- **ID:** F4
- **Severity:** medium
- **Where:** `plugins/specx/skills/plan/SKILL.md:25-27`.
- **Problem:** The check runs only when the header lacks a column. The header is written first. If the run stops after the header write and before the rows are fixed, the next run finds no missing column. The rows stay short for ever.
- **Failure scenario:** The user stops the plan run after the header write. The next plan run sees the full header and skips the upgrade. The table stays broken, and no message tells the user.
- **Remedy:** Make the trigger per row, not per header. For example: "If any row has fewer cells than the header, pad it." Or write the rows before the header. Either change needs a note in the step.
