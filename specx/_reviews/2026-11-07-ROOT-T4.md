## Result

No critical or high findings. 2 medium (one uncertain), 5 low.

ROOT-R25 and T4's "Done when" are met on Linux: with `python3` missing the guard runs through `python`; with no Python 3 a SpecX project (started at its root) gets a `systemMessage` warning; work continues because both scripts always exit 0. The self-check covers both. The target platform for this task, Windows, was not tested by anyone (the builder's log says so too).

## Tests and experiments run

- `python3 /home/w1/specx/plugins/specx/hooks/guard_test.py` from the repo root: `guard ok`, exit 0.
- The same command from `/`: `guard ok`, exit 0.
- Scratch experiments (in the session scratchpad, with a scoped git worktree and an out-of-scope `Edit` payload, `PATH` limited with `env -i`):
  - `python3` is a stub that exits 9009 without reading stdin (like the Windows Store alias), real Python as `python`: guard **denied** correctly through the fallback.
  - `python3` reads all of stdin and then exits 1: no output, exit 0 (fails open; see L2).
  - `python3` runs the guard, prints `deny`, then exits 1: one `deny` line, exit 0 (the `python` fallback got empty stdin and stayed silent, so no doubled JSON).
  - Old command in the same case (`python3 guard.py` exiting 1): `deny` printed but exit 1, which Claude Code treats as a non-blocking error and ignores the JSON. The new wrapper is stricter here, not looser.
  - `python` that exits 1 (stands in for Python 2) and no `python3`: `check-python.sh` warns.
  - Plugin path containing a space: guard ran and denied.
  - `bash run-guard.sh` with no slash in `$0`: silent, guard not found (see L5).
  - `check-python.sh` from a subfolder of a SpecX project with no Python: no warning (see M2).
  - `check-python.sh` output parses as JSON (`python3 -m json.tool`).

## Findings

### M1 (medium, uncertain): the task's target platform, Windows, is untested, and how `bash` resolves there is unverified

- **Where:** `plugins/specx/hooks/hooks.json:9`, `:20` (`bash "${CLAUDE_PLUGIN_ROOT}/hooks/..."`)
- **Breaks:** ROOT-T4 "Why" (Windows) and ROOT-R25 on the platform it exists for.
- **What:** every check, including mine, ran on Linux with simulated `PATH`s. On Windows the hook command now depends on `bash` resolving to Git Bash. If Claude Code runs hook commands through Git Bash (which it needs on Windows), this works. If a hook ever runs through `cmd`/PowerShell, `bash` can resolve to `C:\Windows\System32\bash.exe` (WSL), which cannot see a `C:\...` plugin path, and the guard silently does nothing; the same would hit `check-python.sh`, so no warning shows either. I did not confirm which shell Claude Code uses for hooks on Windows.
- **Scenario:** Windows user with WSL installed and Python installed as `python` only; guard and warning both silently off, the exact case T4 was meant to fix.
- **Remedy:** before release, run the two checks from T4's Verification once on Windows (Git Bash Python missing, and Python as `python` only), or state at the demo that Windows is unverified. If hooks do not run through Git Bash, decide with the user how to invoke the scripts there.

### M2 (medium): a user-visible behavior was logged as an assumption, and it differs from how the guard decides what a SpecX project is

- **Where:** `plugins/specx/hooks/check-python.sh:3-4`; T4 **Assumptions** in `specx/spec.md`
- **Breaks:** RULES rule 1 ("anything the user can see [is] never [an] implementation detail"); ROOT-R25 "in SpecX projects".
- **What:** the warning only appears when the session starts in the folder holding `specx/RULES.md`. `guard.py:50-52` (`is_specx_project`) uses `git rev-parse --show-toplevel`, so the guard treats any subfolder as part of the project but the warning does not.
- **Scenario:** a user opens Claude Code in `myproj/frontend/` of a SpecX project on a machine with no Python 3: no warning, and the guard is off. Confirmed by experiment.
- **Remedy:** either ask the user (small choice) whether the subfolder gap is acceptable, or close it cheaply: before the test, `cd "$(git rev-parse --show-toplevel 2>/dev/null || echo .)"`, matching the guard. Then drop the assumption.

### L1 (low): the version check accepts Python 3.6, but the guard needs 3.7

- **Where:** `plugins/specx/hooks/check-python.sh:6` (`< (3, 6)`); `plugins/specx/hooks/guard.py:45` (`capture_output=True, text=True`, both new in 3.7)
- **Scenario:** only Python 3.6 installed: `subprocess.run` raises `TypeError`, which `guard.py:98` catches and returns silently, so the guard is off and `check-python.sh` reports nothing.
- **Remedy:** change `(3, 6)` to `(3, 7)`.

### L2 (low): guard failures are now completely silent

- **Where:** `plugins/specx/hooks/run-guard.sh:4`
- **What:** `2>/dev/null` on both attempts plus `|| true` hides any guard traceback that used to surface as a non-blocking hook error. Also, if `python3` reads stdin before failing, `python` gets empty input and stays silent (confirmed by experiment). Both fail open, as the old command did, so this is not a weaker guard, but a broken guard is no longer visible.
- **Remedy (optional):** pick the interpreter first, without touching stdin, and run the guard once with stderr visible, for example
  `for p in python3 python; do "$p" -c 'import sys; sys.exit(sys.version_info < (3, 7))' 2>/dev/null && exec "$p" "$guard"; done`.
  This also shares the version rule with `check-python.sh`. Cost: one extra interpreter start (tens of ms) per tool call.

### L3 (low): tests do not cover the most common real-world case

- **Where:** `plugins/specx/hooks/guard_test.py:147-152`
- **What:** the fallback test only covers `python3` absent. It does not cover `python3` present but not working (the Windows Store alias, exit 9009) or `python` being Python 2 for the warning. Line 149 ("python3 still used") does not prove `python3` ran; it would also pass if the fallback produced the output.
- **Remedy:** add a stub `python3` (`#!/bin/sh` + `exit 9009`) next to the `python` symlink and assert `deny`; add a stub `python` that exits 1 and assert the warning. Both pass today by my experiments.

### L4 (low): the warning is not "once per session"

- **Where:** `plugins/specx/hooks/check-python.sh:2`; `plugins/specx/hooks/hooks.json:4-12` (no matcher)
- **What:** `SessionStart` with no matcher also fires on resume, `/clear`, and compaction, so the warning can repeat in one session. The comment says "once per session".
- **Remedy:** fix the comment, or add `"matcher": "startup"` if repeats are unwanted.

### L5 (low): `${0%/*}` fails when `$0` has no slash

- **Where:** `plugins/specx/hooks/run-guard.sh:3`
- **What:** `bash run-guard.sh` run from the hooks folder gives `guard="run-guard.sh/guard.py"`, so the guard silently does nothing. Unreachable from `hooks.json` (always an absolute path, and a Windows backslash root is fine because the last `/` comes from `hooks.json`), so this only affects manual runs.
- **Remedy (optional):** `guard="$(dirname "$0")/guard.py"`.

## Other checks (no finding)

- **Exit codes:** `guard.py` never calls `sys.exit` and never exits 2 on purpose; it signals only through JSON. `run-guard.sh` always exits 0. Previously a missing `python3` gave exit 127, a non-blocking error. No case found where the new wrapper allows something the old command denied.
- **cwd change in tests:** `run()` now uses `cwd=os.sep`. This only affects payloads without `cwd` (lines 63, 68-73), which use `os.getcwd()`. With `/` they no longer pick up a scope from the folder the test runs in (for example a scoped task worktree), so line 73 is now deterministic. No assertion was weakened.
- **Scope:** plugin changes are only under `plugins/specx/hooks/` and `plugin.json`, as T4's Files lists. `specx/spec.md` and `specx/STATUS.md` changes are the main session's bookkeeping. `plugin.json` bumped to 0.5.2; `marketplace.json` has no version field.
- **CI:** `.github/workflows/ci.yml` already runs `python3 plugins/specx/hooks/guard_test.py` on `ubuntu-latest`, which has `bash`, `git` and `python3`; the test creates its own `python` symlink. No CI change needed. The test needs symlinks and `bash`, so it would not run on Windows CI as is.
- **README:** still says only "It needs Python 3" (README.md:55); it does not mention the fallback, the warning or `bash`. ROOT-D32 assigns the README to ROOT-T6, so this is not a T4 gap.
- **Bash requirement:** on Linux and macOS `bash` is always present. On Windows see M1.
