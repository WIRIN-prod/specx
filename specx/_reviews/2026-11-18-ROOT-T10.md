## Findings

**F1 | high | `plugins/specx/skills/plan/SKILL.md:120`**
- **Problem:** The item says "make both match, or turn it into a decision." The planner can choose the wording itself. Rule 2 forbids picking a side when two sources disagree. Rule 1 treats copy and user-visible text as a small choice that needs the user. The item does not say that the user chooses the wording.
- **Failure scenario:** A planner sees two specs with different texts for `409 EMAIL_TAKEN`. It edits the newer spec to match the older one. The user never sees the choice. The build then uses text the user did not approve.
- **Remedy:** Replace the second clause with one instruction, for example: "If two specs describe the same error differently, ask the user which description is correct, and record the answer as a decision." Keep the rule-2 wording.

**F2 | medium | `plugins/specx/skills/plan/SKILL.md:119`**
- **Problem:** "Error row" is not defined. The template has two error tables. Section 6.3 has status, code, and message. Section 6.7 (`plugins/specx/templates/specx/_templates/spec.md:193`) has failure, detection, and user-sees columns, and no body column. The item can apply to both.
- **Failure scenario:** A planner reads item 119 and fails every row in section 6.7, which has no body by design. Or the planner skips section 6.7 and misses a real error body there.
- **Remedy:** Name the table. For example: "Every error row in the Interfaces error table (§6.3) has a literal body." State whether §6.7 rows are in scope.

**F3 | medium | `plugins/specx/skills/plan/SKILL.md:120`**
- **Problem:** "Same error," "description," and "across all specs" are not defined. The item does not say how to identify an error (status and code, or the trigger). It does not say whether "description" means the message text or the whole body. It does not say that the planner must search the other specs.
- **Failure scenario:** Case E: one spec uses `{"detail": "..."}` and another uses `{"message": "..."}` with the same text. One reader fails the item. Another reader passes it because the text is the same. A third reader does not search the other specs, so the conflict is never found.
- **Remedy:** Define the key, for example "same status and code," and state that "description" means the exact body. Add: "Search every `spec.md` in `specx/` before you check this item."

**F4 | medium | `plugins/specx/skills/plan/SKILL.md:119`**
- **Problem:** The item says "exact JSON or exact message text" but does not say what form a text message takes. Quote marks are not required. An unquoted `Email already in use.` (case F) can be read as a literal message (pass) or as words that describe it (fail). An empty body (case G) and a placeholder such as `{"detail": "<reason>"}` have no rule. The item also uses "body" while item 118 uses "message." The two terms are not linked.
- **Failure scenario:** Two reviewers apply the checklist to the same row, case F. One passes it and one fails it. The build agent then guesses the form, which is the failure that ROOT-T5 F16 reports.
- **Remedy:** Define the form in one sentence, for example: "A literal body is a JSON block, or a message in quotation marks, copied exactly." State how an empty body and a placeholder are handled. Say that the message is the body text.

**F5 | medium | Task Verification, `specx/spec.md` ROOT-T10 section**
- **Problem:** The task says "each item names a failing example." Neither new item gives a concrete failing example. Item 119 gives a general rule (words fail). Item 120 gives a condition, not an example.
- **Failure scenario:** The verification step is marked as passed, but no example in the text shows a reviewer what a failing row looks like. The check can be read in different ways, as F3 and F4 show.
- **Remedy:** Add one failing example to each item, for example `409 EMAIL_TAKEN "Email already in use."` in one spec and `409 EMAIL_TAKEN a conflict message` in another. Or record in the task Log that the verification step was changed and get the user's approval.

**F6 | medium | `plugins/specx/templates/specx/_templates/spec.md:135`, and the task Files list**
- **Problem:** The task Files list names `plugins/specx/templates/specx/_templates/spec.md`. The steps do not change it. The template still says "every error with status, code, and message" in the section 6.3 comment. It does not mention a literal body. A spec writer who uses the template gets no guidance for the new item.
- **Failure scenario:** A writer follows the template and writes error rows with status, code, and message only. The check then fails these rows with no matching guidance in the template.
- **Remedy:** Either add the body requirement to the template comment, after the user approves the step change (rule 7), or remove the template from the Files list and log why. Do not make the change without approval.

**F7 | low | `plugins/specx/skills/plan/SKILL.md:119-120`**
- **Problem:** Rule 10 (one instruction per sentence). Item 120 has two instructions joined by "or": "make both match, or turn it into a decision." Item 119 has a fragment in its first sentence: "either exact JSON or exact message text." This is not a complete sentence. The other checks in this section are complete sentences.
- **Failure scenario:** Low. A reader may skip the second instruction. The fragment can be read as a list item and not as a rule.
- **Remedy:** Split item 120 into two sentences, or with F1, use one instruction. Write item 119 as a full sentence, for example: "Every error row has a literal body, which is exact JSON or an exact message text."
