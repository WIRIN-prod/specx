# specX knowledge graph (Obsidian-native)

> **Agents and humans** use the same link graph. Wikilinks in markdown are the API — not a separate index file generated by CLI.

Open this folder (`specx/`) as an **Obsidian vault** for graph view, backlinks, and properties. Every Specialist draft must strengthen the graph.

## Rules (mandatory for agents)

### 1. Wikilinks everywhere concepts connect

Use Obsidian wikilinks **without** the `.md` extension, paths relative to `specx/`:

```markdown
Grounded in [[discovery/01-problem-statement]].
Persona [[discovery/03-personas#Alex]] drives [[discovery/04-user-journeys]].
PRD item → future leaf [[auth/email/registration/FEATURE]].
Upstream capability [[specs/session/spec#Requirement: Valid session]].
Depends on [[auth/core-session/FEATURE]].
```

| Link to | Example |
|---------|---------|
| Discovery phase | `[[discovery/08-prd]]` |
| Foundation | `[[foundation/STEERING]]` |
| Feature leaf | `[[auth/email/registration/FEATURE]]` |
| Feature spec | `[[auth/email/registration/spec]]` |
| Living capability spec | `[[specs/auth/spec]]` |
| Hub | `[[Home]]` |
| Heading in same vault | `[[discovery/03-personas#Primary persona]]` |

### 2. YAML frontmatter on every artifact

Specialist adds or updates frontmatter at the top of each file they write:

```yaml
---
specx:
  layer: discovery | foundation | feature | capability
  phase: "08"              # discovery only
  feature: auth/email/registration   # feature leaf only
  status: pending | in_progress | approved | revision
  artifact: prd | feature | spec | design | tasks
tags: [specx, discovery]
---
```

After human approval, set `specx.status: approved` in that file (in the same PR/commit as `specx approve`).

### 3. `## Graph` section at end of every Specialist output

Every discovery phase, foundation file, and feature artifact ends with:

```markdown
## Graph

| Role | Links |
|------|-------|
| Hub | [[Home]] |
| Upstream (approved only) | [[discovery/07-feature-inventory]], [[foundation/STEERING]] |
| Downstream | [[foundation/BUILD-ORDER]], [[auth/email/registration/FEATURE]] |
| Related | [[discovery/03-personas#Alex]], [[specs/billing/spec]] |
```

Critic verifies links resolve to real paths and match approved prior phases.

### 4. Maintain `[[Home]]` as the map of maps

After each **approved** discovery phase or new **feature leaf**, update `specx/Home.md`:

- Discovery table: phase → wikilink + `specx.status`
- Foundation links
- Feature index (paths from phase 07–08 and `features.yaml`)

### 5. Feature inventory (phase 07) and PRD (phase 08) anchor the product graph

- **07** — each MVP feature is a wikilink to `[[segment/.../leaf/FEATURE]]` (create leaf on propose; link early even if stub).
- **08** — every PRD requirement ID links to a feature leaf or `[[specs/<domain>/spec]]`.
- **BUILD-ORDER** — ordered list of `[[feature-path/FEATURE]]` wikilinks.

### 6. Dependencies = graph edges

In `FEATURE.md` and `features.yaml`, keep the same edges:

```markdown
## Dependencies
- [[auth/core-session/FEATURE]] — required for session cookie
```

Use `specx dep add` for the catalog; **wikilinks** for human/agent navigation.

### 7. What agents read before acting (session bootstrap)

1. `[[Home]]` — where am I in the product?
2. `specx.status` / registry — what is active?
3. **Follow backlinks** from the active feature to discovery + foundation (do not rely on chat memory).

## Anti-patterns

- Plain text feature names with no wikilink when a leaf exists or is planned
- Links to unapproved discovery phases as if they were truth
- Duplicating `features.yaml` in a second index — **Home** summarizes; YAML is for CLI
- Bare URLs instead of `[[internal]]` links for in-repo artifacts
- Skipping `## Graph` because "Obsidian is optional" — **the graph is for agents too**
